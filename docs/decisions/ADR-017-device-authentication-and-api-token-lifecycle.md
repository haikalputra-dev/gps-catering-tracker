# ADR-017: Device Authentication and API Token Lifecycle

- Status: Accepted
- Date: 2026-07-30
- Task Packet: 11
- Related: ADR-016 (customer tracking authentication contrast),
  AR-47 (revised), AR-48, AR-52

## Context

Packet 11 introduces the first machine-to-machine surface in the
project: courier handsets (or a Postman-driven emulator during
prototype) submit GPS pings to a single ingest endpoint. Unlike the
authenticated web UI, the caller is not a person with a browser
session; it is a physical device carried by a courier.

The Project Manager rejected building this on top of the same web
session mechanism because sessions are cookie-scoped and require a
login form, neither of which fits a headless device. The
alternatives considered were:

1. **Reuse the courier's `web` session cookie.** Rejected: couples
   device lifecycle to browser session lifecycle, forces cookies on
   the API surface, and confuses the audit trail because ingest
   would appear to be user-driven.
2. **Full OAuth 2.0 client-credentials flow.** Rejected: gross
   overkill for a two-role prototype with no external clients. The
   authorization server, JWKS, and refresh semantics would dwarf
   the rest of Packet 11.
3. **Laravel Sanctum personal access tokens attached to a User.**
   Rejected: Sanctum's model is per-user, not per-device, and its
   database representation encourages token *lists* per user. AR-50
   requires a strict 1:1 device-to-courier binding with reassignment
   history, so device identity has to be a first-class row anyway.
4. **Hashed device tokens (bcrypt/sha256 in the column).** Rejected
   with AR-47 (revised) as an explicit deviation from the safer
   default: the prototype has no revocation channel, no support
   staff to reissue lost tokens, and no rotation cadence. Hashing
   would eliminate the ability for an owner to re-read the token
   from the admin UI if the courier lost the paper the token was
   written on. The plaintext trade-off is scoped to prototype and
   locked behind a rotation button (see below).
5. **HMAC-signed request bodies with per-device shared secrets.**
   Rejected as unnecessarily complex for the current threat model,
   though the DTO/service separation leaves the door open.

## Decision

### Devices are first-class rows

`devices` is a top-level table (not a pivot on `users`). It carries
its own identifier (owner-visible label), model, hardware version,
`is_active` flag, `notes`, `api_token`, `last_seen_at`, and standard
timestamps. Devices are never deleted; the disable path is
`is_active = false` (AR-50).

Binding to a courier lives on `device_assignments` — a history
table with `assigned_at`, `unassigned_at`, `assigned_by_user_id`,
`unassigned_by_user_id`, and free-form notes. Exactly one row per
device may have `unassigned_at IS NULL` at any time (enforced by
`DeviceAssignmentService` under `SELECT ... FOR UPDATE`), and a
courier may appear in at most one open row across all devices
(AR-50). These invariants are covered by the unit-test suite in
`tests/Unit/Domain/Device/DeviceAssignmentServiceTest.php`.

### Bearer token, plaintext, `hash_equals` compare (AR-47 revised)

Devices authenticate with `Authorization: Bearer <token>`. The
token is generated by `App\Domain\Device\ApiTokenGenerator` from a
configurable alphabet and length (defaults: 40 chars, 62-char
alphanumeric alphabet). Both are enforced with a minimum floor
(length ≥ 16, alphabet ≥ 16 chars) so an accidental configuration
error cannot degrade entropy silently.

`AuthenticateDeviceToken` middleware:

1. Extracts the token from `Authorization: Bearer <token>`, using a
   case-insensitive scheme match and rejecting empty tokens.
2. Queries `devices` for a matching plaintext token.
3. Applies `hash_equals` between the stored and presented values
   even after the equality-based `WHERE` clause has already returned
   the row. This is defence in depth: if the storage backend ever
   moves to a hashed representation, the middleware's contract is
   already constant-time on the final compare.
4. Rejects requests bound to inactive devices with the same 401
   response as an unknown token.

All 401 responses carry a single generic message
(`{"message":"Invalid device token."}`) so the endpoint cannot be
used as an oracle for token enumeration or device presence.

The resolved `Device` is attached to the request via
`$request->attributes->set('device', $device)` so the throttle
limiter and controller can reuse it without a second query.

### One-shot token disclosure

The plaintext token is displayed to the owner exactly once at each
generation event:

- After successful `POST /devices` (registration).
- After successful `POST /devices/{device}/rotate-token`.

Disclosure uses a one-shot flash key (`token_plain`) so the next
render of the show page does not re-expose the value. The `Device`
model marks `api_token` as `$hidden`, so any accidental
serialization to a view or API response omits it by default.

### Rotation is a first-class action, not an edit

Token rotation is a dedicated `POST /devices/{device}/rotate-token`
route with its own controller action, not folded into the update
form. This keeps the audit intent unambiguous: an owner who rotated
a token can be recognized in server logs by a distinct request
pattern rather than a diff on the token column.

Deactivating a device with the update form automatically closes
any open assignment (`DeviceAssignmentService::unassign` with a
"device deactivated" note). This is the recovery path when a
handset is lost: deactivate the device, rotate the token if you
still have the row, then register a replacement.

### Combined web / ingest scope on the same host (AR-52)

`POST /api/telemetry` is registered in `routes/web.php` behind the
`device.auth` and `throttle:telemetry` aliases. There is no
separate API subdomain, no Sanctum guard, no per-guard auth
provider. The web session middleware group is not applied to the
route; only the two aliases above are.

`bootstrap/app.php` configures
`shouldRenderJsonWhen(fn ($r) => $r->is('api/*'))` so
authentication failures, validation failures, and throttle
exceptions on this route are rendered as JSON instead of HTML.

### Middleware priority is explicit

Laravel's default middleware priority places `ThrottleRequests`
before non-prioritized middleware. Without an explicit priority
declaration, the `telemetry` limiter callback fires before
`AuthenticateDeviceToken` has resolved the token, so the limiter
sees `null` for the device attribute and silently falls back to
IP keying. That would defeat AR-49 and cause co-located devices
to share a single quota.

`bootstrap/app.php` calls `prependToPriorityList` to hoist
`AuthenticateDeviceToken` above `ThrottleRequests` in the priority
list. `tests/Feature/Telemetry/TelemetryRateLimitTest` includes an
explicit per-device scoping test that fails if the priority
declaration is removed.

## Consequences

### Positive

- Machine callers authenticate without any browser artifact
  (cookies, CSRF, session id). The route lives on the same host,
  keeping deployment topology simple.
- The Device row is the canonical audit unit. Every accepted or
  discarded submission bumps `devices.last_seen_at`, so an owner
  looking at the device index can see freshness even for idle
  couriers.
- Token rotation, deactivation, and reassignment are all
  independent, minimal actions; each maps to a single controller
  method with a single form request.

### Negative

- Plaintext token storage is a deliberate prototype trade-off.
  A database dump exposes usable credentials. The remediation is
  documented as rotation via the admin UI, not encryption at rest.
- No token expiry: a lost handset that still holds a valid token
  keeps talking until the owner deactivates the device or rotates
  the token. Field procedure must include a "report lost device"
  step; documenting that procedure is outside the code scope of
  Packet 11.
- Because middleware priority is a global setting, adding new
  Bearer-authenticated routes later will inherit the same
  ordering. That is a feature, not a bug, but the priority hoist
  must be preserved by any future middleware refactor.

## Compliance surface

- **AR-47 (revised):** plaintext storage, `hash_equals` compare,
  one-shot disclosure at generation and rotation, `$hidden` on
  serialization.
- **AR-48:** device rows are audit-first — `last_seen_at`,
  `is_active`, and full assignment history are all preserved.
- **AR-50:** 1:1 device-to-courier binding with full history;
  invariants under lock; deactivation auto-unassigns.
- **AR-52:** combined-scope route on the web host, JSON exception
  rendering scoped to `api/*`, no separate API auth stack.

## Alternatives considered

Enumerated under Context above. All were rejected before
implementation began. The domain services (`ApiTokenGenerator`,
`DeviceAssignmentService`) and the middleware are small enough that
migrating to a hashed-token scheme, adding token expiry, or moving
to a signed-request contract would not require rewriting the
controllers or routes.
