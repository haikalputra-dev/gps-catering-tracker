# ADR-008: Kitchen Lifecycle and Coordinate Selection

- Status: Accepted
- Date: 2026-07-30
- Deciders: Product Manager, Tech Lead
- Related: ADR-003 (free mapping stack), ADR-007 (role-based session auth),
  AR-21 (kitchen lifecycle)

## Context

Task Packet 05 introduces the first business entity beyond user accounts:
the kitchen. Kitchens anchor future work on delivery, tracking, and pricing.

Two design questions had to be settled in this packet:

1. How is a kitchen removed?
2. How does the operator pick a kitchen's coordinate?

Prior decisions constrain the answers:

- ADR-003 forbids paid mapping providers.
- ADR-007 established that only owner and staff roles administer data;
  couriers do not.
- AR-16..AR-20 in the decision log were generated by Packet 04 without
  PM approval and are now recorded as Void.

## Decision

### Lifecycle: active/inactive, no delete

Kitchens carry an `is_active` boolean. Owners and staff can flip this
value through the edit form. There is no delete route, no destroy
controller action, no soft-delete column, no restore path, and no
delete button in the UI. `DELETE /kitchens/{id}` returns HTTP 405
because the route is not registered.

The rationale:

- Kitchens are referenced by future delivery, tracking, and pricing
  records. Deleting a kitchen would leave those references dangling or
  force cascade behavior we are not ready to specify.
- Historical reporting requires the record to remain even after a
  kitchen closes.
- `is_active` is simpler than soft-delete because it does not affect
  uniqueness of the code column.

### Coordinate selection: local Leaflet on configurable OSM tiles

Coordinates are chosen with Leaflet 1.9.4, bundled through Vite. The
default tile layer is the public OpenStreetMap standard raster service.
Tile URL, attribution, default center, default zoom, selection zoom,
and maximum tile zoom are configurable via `config/map.php`, backed by
`MAP_*` environment variables.

The rationale:

- Leaflet is MIT-licensed, small, and does not require a paid provider.
- Bundling through npm removes CDN availability as a failure mode and
  keeps the app usable offline of external CDNs during local dev.
- Making the tile URL configurable lets operators switch providers
  without a code change if OSM's community tile policy becomes a limit.
- Server-side validation is the authoritative check. The map is an
  input aid; the numeric fields still have to pass request validation.

### Explicitly excluded

- No geocoding (Nominatim or otherwise).
- No browser geolocation.
- No routing, polygons, or search.
- No Google Maps or other keyed providers.
- No public or API endpoints for kitchens.
- No relationships to customers, deliveries, prices, tracking, devices,
  or SMS.

## Consequences

### Positive

- The kitchen surface is intentionally small: 5 routes, no delete path,
  no third-party integrations. It sets a clean foundation for later
  packets.
- Deactivation is reversible with no data loss.
- Coordinate authority is the server, so any future non-web client
  (mobile, importer) inherits the same rules.
- Zero recurring cost for maps.

### Negative

- Operators cannot fully remove a kitchen record. This is deliberate;
  cleanup is a manual database task if it is ever required.
- OSM's public tile service has no SLA. Production traffic beyond the
  prototype scale will require a different `MAP_TILE_URL`.
- Selecting a coordinate away from familiar landmarks requires the
  operator to scroll and zoom manually because there is no search.

### Neutral

- Requires future delivery/tracking packets to check `is_active` on
  the kitchen before scheduling work.
- Existing coordinate values will migrate cleanly because
  `decimal(10, 7)` provides ~1 cm precision, well beyond consumer GPS.

## Alternatives considered

- **Soft-delete via `deleted_at`.** Rejected: adds complexity without
  giving anything `is_active` does not, and it complicates uniqueness
  of the code column.
- **Google Maps JavaScript API.** Rejected under ADR-003 (no paid
  providers) and would require key management the prototype does not
  have.
- **Address-based storage with geocoding on save.** Rejected: adds a
  network dependency and puts an external service in the write path.
